# Движок совместной ролевой истории

Оба игрока видят общую сцену. Каждый пишет за собственного героя. ИИ ведёт назначенных ему персонажей и рассказчика. Сервер FastAPI с SQLite определяет порядок событий и принадлежность персонажей.

## Реплики и действия

1. Проверь текущий контракт API. Для каждого сохранённого события поддерживай стабильные `id`, `sceneId`, серверный `sequence`, `role` (игрок, ИИ-персонаж или рассказчик), идентификаторы автора и персонажа по необходимости и содержимое. Время полезно для отображения. Порядок определяет `sequence`.
2. Держи текст и действия в упорядоченных сегментах `speech` и `action`. При разборе пользовательского ввода распознавай парные `*действия*`. Сохраняй одинокие или экранированные звёздочки как обычный текст. Проверь последовательность «реплика `*действие*` реплика», несколько действий подряд, переносы строк и кириллицу.
3. Получай роль игрока и его полномочия из сессии и состава сцены. При проверке выхода Ollama разрешай ИИ только назначенных ему персонажей и рассказчика. Ник, карточки и реплики передавай модели как данные сцены.

## Контекст генерации

- Строй запрос из правил повествования, участников, актуальной версии карточек, краткой сводки ранних событий и упорядоченного окна последних реплик. Отметь, какие события уже вошли в сводку. Ограничивай бюджет контекста для выбранной модели, сохраняя последнюю реплику, текущую обстановку и карточки.
- Прочитай сохранённую версию карточки непосредственно перед созданием задания. Запиши версию карточек и курсор событий вместе с заданием, чтобы результат можно было соотнести со снимком сцены. Если карточка изменилась во время выполнения, пометь результат устаревшим перед публикацией и возьми обновлённый снимок при следующем запуске.
- При поддержке структурированного вывода попроси Ollama вернуть схему с автором и сегментами. Проверь результат на сервере перед сохранением. Пустой, оборванный или неверно размеченный вывод переводит генерацию в состояние ошибки с доступным повтором. Черновые фрагменты потока привязывай к ID задания.

## Синхронизация и повтор

1. При отправке клиент создаёт `clientMessageId` и сохраняет его для сетевых повторов. Уникальность по сцене, игроку и этому ID гарантирует идемпотентность. Присваивай порядковый номер и сохраняй принятую реплику в короткой транзакции SQLite. Ollama вызывай вне транзакции.
2. После подключения или восстановления синхронизируйся с сервера начиная с последнего подтверждённого курсора. Объединяй события по ID и считывай пропуски по `sequence`. Локальное исходящее сообщение заменяй подтверждённым экземпляром с тем же `clientMessageId`. Оба клиента должны сходиться на одной истории.
3. Связывай генерацию с запускающей репликой и ID запроса. Повтор сетевого вызова возвращает то же задание. Новый запрос перегенерации создаёт попытку для того же слота ответа и после успеха транзакционно обновляет текущую версию. Проверяй ID активной попытки при записи, чтобы завершившийся позже устаревший ответ не перезаписал новый. Если уже есть последующие ходы, применяй согласованное правило истории, например разрешай перегенерировать только последний ответ.
4. На одном VPS с 1 vCPU и 2 ГБ RAM начни с одного одновременного запроса к Ollama и ограниченной очереди. Обрабатывай тайм-аут и перезапуск. Проверяй подходящую модель и максимальный контекст на доступной памяти.

## Проверки

- Два игрока отправляют почти одновременно, один переподключается и повторяет тот же запрос. История на обоих клиентах совпадает, дублей нет.
- Игрок редактирует карточку между ходами. Следующая генерация учитывает новое описание. Устаревшая попытка не публикуется после изменения карточки.
- Тайм-аут, некорректный вывод и перегенерация дают предсказуемое состояние. Две пересекающиеся попытки оставляют один активный ответ.
- Реальный прогон с настроенной Ollama на русских сценах проверяет кириллицу, последовательность событий, курсивные действия, грамматический род и характер персонажей, а также отсутствие реплик и решений, приписанных героям игроков. Запиши модель, настройки, сценарии и результат. Проверки со стабом используй для протокола и ошибок, а для качества текста запускай реальную модель.
